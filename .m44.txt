content: a binary upload is read from the repository, not the process

`changeset_from_content` took a tree path - the same string that goes into
`changeset_files` - and read it with `std::fs::read(path)`. That resolves against
the server process's working directory, so the answer depended on where the
process was started: correct when the cwd happened to be the repo root, a
different file when a same-named file sat there, and `No such file or directory`
everywhere else. Nothing in the signature said the two paths differed, and the
comment claimed the caller passes a path on disk when the one caller never did.

It takes `root: &Path` now and reads `root.join(path)`. The tree path and the
path on disk are the same value with the repository prefixed, which is what a
repository is.

One thing clippy caught: adding `root` made the function eight arguments, past
the seven-argument limit. The lazy fix is an attribute; the honest one is that
the database and the root are the same thing - a repository - and every function
that needs both was passing one and forgetting the other. `Repo<'a> { conn,
root }` is seven arguments, [Copy], and it makes the second half impossible to
omit. The limit is a prompt to find the missing concept, not an obstacle to
route around.
